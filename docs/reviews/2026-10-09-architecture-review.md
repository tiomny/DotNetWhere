# Код-ревью архитектуры DotNetWhere

Дата: 2026-10-09.

Объект ревью: текущее рабочее дерево после рефакторинга Core / Application / Infrastructure / CLI.
Замечания относятся к этому состоянию, включая ещё не закоммиченные файлы.

Ревью включает проверку направления зависимостей, DI, контрактов, нормализации NuGet-графа,
управления процессами, отмены, вывода и тестов. Исправления во время ревью не выполнялись;
дополнительные воспроизведения создавались в `/tmp`.

Приоритеты:

- **P2** — функциональный дефект, требующий исправления.
- **P3** — архитектурный недостаток или риск в ограниченном сценарии.
- **Ограничение** — поведение, для изменения которого требуется определить семантику продукта.

## Подтверждённые дефекты

### R01. P2 — Экспоненциальное разворачивание графа при подготовке вывода

Место: `src/DotNetWhere/Rendering/SolutionOutput.cs:17`.
Связанные места: `Rendering/CompactFormatter.cs:10`, `ColorFormatter.cs:12`, `JsonFormatter.cs:17`.

Поиск кеширует общие зависимости, но `PackageOutput.From` заново копирует каждое поддерево для каждого пути.
Даже Compact сначала полностью строит DTO. Color затем создаёт отдельное дерево Spectre.Console,
а Json дополнительно формирует полную строку результата.

Воспроизведение: послойный ациклический граф, где два пакета каждого слоя ссылаются на оба пакета
следующего слоя. Для 32 пакетов преобразование создало 65 535 вхождений пакетов;
для 36 пакетов — 262 143 вхождения и около 24 МиБ выделений только на DTO.

Последствие: небольшой входной граф вызывает большой расход памяти ещё до начала записи результата.
Количество путей само по себе может быть экспоненциальным, поэтому одного ускорения поиска недостаточно.

Направление исправления: Compact должен обходить результат напрямую, Json — писать последовательно.
Для количества выводимых путей нужен явный предел с диагностикой; молча обрезать результат нельзя.
Нужно отдельно определить допустимое потребление памяти для Color, которому требуется дерево представления.

### R02. P2 — Неограниченная рекурсия аварийно завершает процесс

Место: `src/DotNetWhere.Core/Search/DependencySearch.cs:31`.
Связанные места: `src/DotNetWhere/Rendering/SolutionOutput.cs:17`, `CompactFormatter.cs:22`,
`ColorFormatter.cs:42`.

Обнаружение циклов работает, но глубина корректного ациклического графа ничем не ограничена.
Обход поиска, преобразование результата и текстовые форматтеры используют рекурсию.

Воспроизведение: искусственная цепочка из 1 000 пакетов обработалась успешно;
цепочка из 10 000 пакетов вызвала `Stack overflow` и аварийное завершение процесса на Linux.
В тестовом воспроизведении создание core dump было отключено.

Последствие: CLI не может преобразовать такой сбой в обычную ошибку анализа.

Направление исправления: обход с явным стеком; если вводится ограничение глубины,
оно должно проверяться и возвращать управляемую ошибку. Проверить также весь путь вывода результата.

### R03. P2 — Отмена не распространяется на подготовку и запись результата

Места: `src/DotNetWhere/Cli.cs:58`, `src/DotNetWhere/Rendering/IOutputFormatter.cs:8`.

CLI проверяет токен перед выводом, но интерфейс форматтера не принимает токен.
Преобразование DTO, построение дерева и запись после этой проверки не реагируют на отмену.

Воспроизведение: writer отменял токен на первой строке Compact. CLI продолжил запись,
вывел 258 строк и вернул код 0 при отменённом токене.

Последствие: Ctrl+C во время большого вывода не останавливает операцию и может завершиться кодом успеха.

Направление исправления: передавать токен через преобразование, обход и запись,
проверяя его во время длительной работы; сохранять код 130 для отменённой операции.

### R04. P2 — Потомки остаются работать после завершения родителя

Место: `src/DotNetWhere.Infrastructure/DotNetProcessRunner.cs:50`.
Связанный тест: `tests/DotNetWhere.Tests/InfrastructureTests.cs:109`.

При отмене или таймауте дерево процессов уничтожается только при `!process.HasExited`.
Если родитель уже завершился, а потомок продолжает держать stdout/stderr, уничтожение пропускается.

Воспроизведение: fixture `leave-child` завершает родителя и оставляет потомка с открытыми потоками.
После таймаута в одну секунду runner вернул `ProcessFailed`, но потомок оставался в состоянии
`S (sleeping)`. Созданный для проверки потомок затем был принудительно завершён.

Существующий тест самостоятельно убивает оставшегося потомка в `finally` на строках 136–150.
Он проверяет своевременный возврат, но не гарантирует очистку runner-ом.

Направление исправления: определить механизм владения группой процессов, сохраняющий возможность
завершить потомков после выхода родителя. Простое повторное обращение к завершившемуся родителю
не восстанавливает информацию о потерянном дереве. Проверка должна различать возврат runner-а
и фактическое завершение потомков.

Согласно [документации Process.Kill](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.kill?view=net-10.0),
ожидание завершения родителя не подтверждает завершение его потомков.

### R05. P2 — Ошибка очистки временного каталога подменяет первичную ошибку

Место: `src/DotNetWhere.Infrastructure/NuGetDependencyGraphSource.cs:43`.

Незащищённый `Directory.Delete` в `finally` может заменить ошибку процесса, чтения или отмену.
Исключение из `finally` обходит расположенный выше обработчик ошибок источника.

Воспроизведение: контролируемый msbuild завершился с кодом 17 и оставил защищённый дочерний каталог.
Источник выбросил `UnauthorizedAccessException` вместо исходного `GraphSourceException(ProcessFailed)`.
Тот же путь способен подменить `OperationCanceledException`.

Направление исправления: сохранять первичную причину сбоя и отдельно сообщать об ошибке очистки.
Явно определить поведение при ошибке очистки после иначе успешной операции.

### R06. P2 — Недостаточная проверка структуры внешнего графа

Места: `src/DotNetWhere.Infrastructure/AssetsGraphReader.cs:20` и `AssetsGraphReader.cs:60`.

Адаптер проверяет некоторые поля, но не всю обязательную структуру данных NuGet.

Подтверждённые воспроизведения:

- Синтаксически корректный JSON с проектом без `restore` вызвал сырой `NullReferenceException`.
- Отсутствующее поле `projects` превратилось в пустой граф.
- Неизвестный или отсутствующий тип зависимой библиотеки молча исключил ребро из графа.

Последствие: повреждённые данные могут выглядеть как отсутствие пакета либо попадать в общий
обработчик CLI, обходя структурированный результат Application и JSON-конверт ошибок анализа.

Направление исправления: проверять обязательные поля и допустимые типы на границе адаптера,
возвращая ошибку некорректных входных данных. Не добавлять `NullReferenceException` в общий `catch`:
это скроет отсутствие валидации и может замаскировать дефекты самого адаптера.

### R07. P2 — Решения .slnx ошибочно отклоняются

Место: `src/DotNetWhere.Infrastructure/NuGetDependencyGraphSource.cs:49`.

Проверка каталога допускает только `.csproj` и `.sln`. Решение `.slnx` с проектами в подпапках
отклоняется до вызова dotnet.

Воспроизведение на SDK 10.0.401: `dotnet new sln` создал `Modern.slnx`.
CLI вернул `InvalidDirectory` и код 1, хотя restore этого решения и генерация restore graph проходили.

Направление исправления: поддержать `.slnx` и проверить каталог, в котором есть только решение
и подпапки проектов. В .NET 10 этот формат используется по умолчанию для `dotnet new sln`:
[документация изменения](https://learn.microsoft.com/en-us/dotnet/core/compatibility/sdk/10.0/dotnet-new-sln-slnx-default).

### R08. P3 — Неверный таймаут проверяется после запуска процесса

Место: `src/DotNetWhere.Infrastructure/DotNetProcessRunner.cs:37`.

`CancellationTokenSource` для таймаута создаётся после `process.Start()`.
Значение `TimeSpan.FromMilliseconds(-2)` вызывает `ArgumentOutOfRangeException`,
когда процесс уже запущен, и оставляет процесс или его дерево работать.

Воспроизведение подтверждено через публичный API Infrastructure. Текущие значения по умолчанию CLI
не позволяют пользователю вызвать этот сценарий.

Направление исправления: проверять конфигурацию до запуска; после успешного запуска учитывать
владение процессом на всех путях выхода, включая ошибки вне обработчика отмены.

## Архитектурные замечания

### R09. P3 — Application знает детали механизмов поиска и источника

Места: `src/DotNetWhere.Application/AnalyzeDependencies.cs:43`, `AnalysisError.cs:8`,
`GraphSourceException.cs:3`, `IDependencyGraphSource.cs:7`.

Сценарий ловит `RegexMatchTimeoutException`, хотя механизм сопоставления инкапсулирован в Core.
Общий набор ошибок содержит `ProcessFailed` и `InvalidAssets`, привязывающие контракт к текущему
способу загрузки графа. `GraphSourceException` принимает любой `AnalysisErrorCode`, включая
`InvalidFilter` и `PackageNotFound`, которые источник производить не должен.

Это семантическое протекание абстракций, а не прямая зависимость Application от Infrastructure.
У порта также не описан ожидаемый контракт ошибок и отмены.

Направление исправления: Core должен предоставлять собственную ошибку фильтра;
порт источника — собственный ограниченный набор ошибок загрузки графа.
Технические сведения о процессе и assets следует сохранять в диагностике, отдельно от общего контракта.

### R10. P3 — Терминология формата вывода проникла в модель Core

Место: `src/DotNetWhere.Core/Models/Target.cs:8`.

`Target.Version` содержит framework вроде `net10.0`, хотя входная модель правильно называет
это значение `Framework`. Историческое имя JSON-поля определяет терминологию внутренней модели.
Общие имена `Solution`, `Project`, `Package` также слабо отличают результат поиска от входного графа.

Направление исправления: использовать `Framework` внутри Core и сохранить JSON-поле `Version`
в адаптере вывода. Рассмотреть имена `SearchResult`, `MatchedProject`, `MatchedPackage`.
Само наличие результата поиска и признака `IsMatch` в Core допустимо.

## Ограничения семантики и дополнительные риски

### R11. Ограничение — Не отображаются пути через ProjectReference

Место: `src/DotNetWhere.Infrastructure/AssetsGraphReader.cs:64`.

В реальном примере `A → проект B → Newtonsoft.Json` resolved assets проекта A содержат пакет,
но A получает пустые roots и отсутствует в результате. Проект B отображается.
Нормализатор исключает проектные библиотеки и выбирает только прямые пакетные корни.

До изменения нужно определить, должен ли инструмент показывать проекты-потребители,
которые получают пакет через ссылку на другой проект. Это унаследованное ограничение семантики,
а не доказанная регрессия рефакторинга.

### R12. Ограничение — RID-зависимости не представлены

Место: `src/DotNetWhere.Infrastructure/AssetsGraphReader.cs:42`.

Выбирается только target без `RuntimeIdentifier`. Текущий контракт графа не позволяет представить
различия runtime targets и соответствующие пути зависимостей. Изменение требует решения
о поддержке поиска по RID и о формате представления результатов.

### R13. Риск — Логи процессов неограниченно накапливаются в памяти

Место: `src/DotNetWhere.Infrastructure/DotNetProcessRunner.cs:39`.

Оба потока читаются целиком через `ReadToEndAsync`, после чего объединяются в сообщение ошибки.
Источник с большим объёмом вывода способен существенно увеличить расход памяти.
Это вывод из кода; отдельное нагрузочное воспроизведение для логов не выполнялось.

Направление исправления: ограниченный буфер последних диагностических сообщений;
при необходимости полный лог — отдельный поток или файл с определённым владельцем.

### R14. Риск — Запись результата в файл не атомарна

Место: `src/DotNetWhere/Cli.cs:65`.

`new StreamWriter(options.OutputFile)` обнуляет существующий файл до завершения форматирования и записи.
Ошибка записи после успешного анализа уничтожит предыдущий результат или оставит частичный файл.
Это вывод из кода; отдельная проверка заполненного диска не выполнялась.

Направление исправления: записывать во временный файл рядом с назначением, закрывать его
и заменять назначение только после успешного завершения. Учитывать отмену и очистку временного файла.
Существующее сохранение файла при неудачном анализе работает и должно остаться.

### R15. Недостаток проверок — Архитектурный тест и проверки процессов не покрывают контракты полностью

Места: `tests/DotNetWhere.Tests/CliTests.cs:207`, `InfrastructureTests.cs:83`,
`InfrastructureTests.cs:109`, `ProcessFixture.cs:59`.

Архитектурный тест проверяет ограниченный список запрещённых ссылок в собранных assemblies.
Он не доказывает отсутствие семантических протеканий, не охватывает все внешние зависимости
и не обнаруживает неиспользуемые ссылки проектов или пакетов.

Тест открытых потоков потомка выполняет самостоятельную очистку, не утверждая, что её выполнил runner.
Проверка завершения потомка сразу после возврата runner-а нестабильна: ожидание родителя
не гарантирует завершение всех потомков. Ожидание появления файла fixture также не гарантирует,
что файл полностью записан или родитель уже завершился.

Направление исправления: проверять фактический контракт каждой границы; синхронизировать fixture
по проверяемому состоянию, использовать ограниченное ожидание завершения потомка и оставить
защитную очистку теста после утверждений. Архитектурные проверки дополнить правилами допустимых
зависимостей проектов и типов. Добавить проверки больших графов, отмены вывода и повреждённых данных.

## Что не является обнаруженным нарушением

- Текущие регистрации в `CompositionRoot` не содержат параметров отдельного запроса.
- Singleton хранит неизменяемую конфигурацию процесса; захвата scoped-сервисов не обнаружено.
- Параметры поиска передаются в `ExecuteAsync`, поэтому повторные запросы не требуют нового контейнера.
- Разрешение `Cli` в точке входа соответствует роли composition root.
- Конкретные вспомогательные зависимости внутри Infrastructure допустимы.
- `switch` фабрики форматтеров сам по себе не является доказанным нарушением OCP.
- Результат поиска и `IsMatch` могут находиться в Core; проблема R10 касается терминологии контракта.
- `FileSystemName.MatchesSimpleExpression` сопоставляет строки и сам по себе не выполняет файловый I/O.
- `ArgumentList` корректно обрабатывает аргументы с пробелами.
- Владение output streams, сохранение файла при ошибке анализа и маршрутизация ошибок соответствуют README.

## Проверки и ограничения доказательств

Полный прогон выполнялся командой:

```bash
dotnet test -c Release --artifacts-path /tmp/dotnetwhere-architecture-artifacts \
  --no-restore --disable-build-servers
```

- Первый полный прогон: 55 успешных, 1 упавший из 56.
- Упал `Run_CancelledParent_StopsItsDescendants` на проверке `child.HasExited`.
- Отдельный повтор этого теста: успешно.
- Второй полный прогон: 56 успешных из 56.
- Падение не удалось стабильно повторить; асинхронное завершение потомков объясняет риск проверки,
  но точный тайминг первого падения не был зафиксирован.
- Дополнительные воспроизведения поиска, вывода, процессов и нормализации выполнялись отдельно в `/tmp`.
- Процессные воспроизведения проведены на Linux; эквивалентные проверки на Windows не выполнялись.
- Номера строк относятся к состоянию файлов на дату ревью и могут измениться после исправлений.
